## Stage 0 scope (SPEC §12, Stage 0 — Foundations)

Build only the data-semantics foundation. **No API, no UI, no model training in this stage** (those are Stages 1–2). Deliver:

1. **Repository scaffold**
   - Python 3.11+ package `rankflow/` with `pyproject.toml`, lockfile, `.gitignore` (data, artifacts, secrets), `.env.example`, `README.md` (project identity, claims discipline from SPEC §1/§11, data license attribution for OTTO, CC BY 4.0).
   - Layout following SPEC §13 where it applies to this stage (`training/` data-prep modules may live under `rankflow/data/` if cleaner — record the choice in README).
   - `configs/stage0.yaml` for every frozen configuration value used below (no magic numbers in code).

2. **Synthetic fixture (do this first; all tests run on it)**
   - A small, deterministic, OTTO-format fixture (JSONL: `session`, `events[{aid, ts, type}]`) under `tests/fixtures/`, clearly synthetic, generated by a committed script with a fixed seed. It must include: same-millisecond events in one session, repeated items, reversed-order occurrences, horizon-boundary occurrences, a session crossing a window boundary, and sessions long enough to exercise the pair-builder caps.

3. **Ingestion and event identity (Addendum R21)**
   - Loader that streams OTTO JSONL and assigns a persistent **`event_index`** per session, ordered by `(ts, original file order)` — timestamps alone never define order.
   - Deterministic session sampler: hash-based selection with a configured cap, so the same config always selects the same sessions. Record selected session IDs and the source file hash in the manifest.

4. **Window scheme and manifests (SPEC §3.2 R5; Addendum R22/F05)**
   - Chronological windows W0 (statistics/history), W1 (training), W2 (validation; split deterministically by session hash into **W2-dev / W2-gate** per Addendum R27), W3 (final test).
   - Sessions crossing a window boundary are excluded from both adjacent governed windows and **counted** (window-exclusion accounting by session-length distribution).
   - A versioned **data manifest** (JSON): window boundaries, session ID lists or their hashes, counts, exclusion counts, source hash, sampler config, retrieval parameters (see 6), and content hashes of every produced artifact.

5. **Evaluation epoch registration (Addendum R22, F05)**
   - An `EvaluationEpoch` record (fields per Addendum R22) with a validator that **rejects** registration when any F05 inequality fails: snapshot watermark < min query cutoff; every training label time < W2 start; W1 labels are the first click strictly after the cutoff `event_index`; W2-dev/W2-gate/W3 pairwise disjoint and ordered; window-crossing sessions excluded. Rejection must name the violated predicate.

6. **Query and label generation (Addendum R26, label policy `nextclick-v1`)**
   - For each eligible cutoff position (min prefix length and max cutoffs per session from config), emit a query record keyed by **`(session_id, cutoff_event_index)`** with prefix events, cutoff timestamp, epoch/snapshot reference, and `positive_aid` = first click strictly after the cutoff position, or none.
   - Every row records `source`, `label_policy_version`, and epoch. Queries are reproducible byte-for-byte from the manifest + config.

7. **Exact co-visitation build (SPEC R2/R21; Addendum R28/F06/C04)**
   - Canonical unordered pairs: for positions `i < j`, `0 < j − i ≤ H` (config, default 20), `aid_i ≠ aid_j`, pair = `(min, max)`; a pair qualifies if **any** occurrence qualifies; per session each canonical pair counts **exactly once**.
   - Implementation must be **disk-based exact aggregation** (e.g., chunked pair emission into SQLite, then GROUP BY) — no in-memory full pair map, no approximate/streaming top-N claims. Sessions are truncated for pair generation at the configured event cap (default 500). Enforce the configured **disk budget**: abort with a report if exceeded.
   - After exact counting, select top-N per item (config) with a minimum count threshold. The retrieval snapshot manifest records: `H`, session cap, pair-definition version, disk budget, source hash, table row count, on-disk size, pruning config (SPEC R2).

8. **Validators and tests (all must pass; tests are the stage's evidence)**
   - **T09:** same-millisecond events → unique `(session_id, cutoff_event_index)` query IDs; replay order preserved.
   - **T17:** epoch registration rejects (a) W2/W3 intersecting a training label horizon, (b) a snapshot newer than a query cutoff, (c) overlapping W2/W3 windows.
   - **T18:** the fixture's repeated/reversed/tied/horizon-boundary session produces exactly the pair counts specified by the R28/F06 definition (hand-computed expected values in the test).
   - **Future-event mutation test (R5):** appending or modifying events after a query's cutoff, or in a later window, does not change that query's candidate inputs or feature-relevant prefix data.
   - **Leakage checks:** no query's statistics snapshot contains events at or after its cutoff (the R5 invariant, asserted over the whole fixture query set).
   - Determinism test: two runs from the same manifest/config produce identical query sets and identical co-visitation tables (hash comparison).

9. **Data-validation report**
   - A generator producing `docs/data_validation_report.md` (+ JSON) from a run: window counts, exclusion accounting, query counts by window, label coverage (queries with/without a retrieved positive), co-visitation table stats, and the pass/fail of every invariant above. Run it on the fixture and commit the fixture report.

10. **Product contract draft**
    - `docs/product_contract.md`: the Stage 0 exit-gate draft of the Playground/Console UX and API contract (personas, the §6.4 interaction loop, claims/non-claims) — document only, no implementation.

## Data download

- `scripts/fetch_data` downloads the OTTO dataset from the official source (github.com/otto-de/recsys-dataset), records file hashes, and never commits raw data. If the full download is impractical in this session, the script plus the fixture path must still be complete and tested; record the download status honestly in the report — do not fabricate a real-data run.

## Acceptance (Stage 0 exit gate, SPEC §12)

- Data-validation report exists (fixture run committed; real-data run when data is fetched).
- Query set is deterministic and reproducible from the manifest.
- Replay of a recorded session prefix is leak-free (mutation + invariant tests green).
- Product contract draft written.
- Full test suite passes; work is committed in small, reviewable commits.

## Hard constraints

- No Kafka, Kubernetes, MLflow, or LLM anything. No new subsystems beyond this stage.
- Do not use demo/synthetic data in any real-data artifact; label provenance everywhere (`source` field).
- Never claim metrics, benchmarks, or real-data results that were not actually produced in this run.
